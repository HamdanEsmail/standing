## Constraints added during the build

- 3 Nov: Standing keeps at most one TinyAgent run in flight at any time, because my builds share the account's limit of 2 concurrent runs. A second check's run queues behind a pending one in a D1 slot with a 5-minute stale timeout; Monitor-triggered re-checks share the same slot. A 429 `RATE_LIMIT_EXCEEDED` waits 60 s and retries up to 3 times. Added to the plan's Task 7.
- 3 Nov: a single returned row is a match only when its name passes the match rule; otherwise ambiguous with that one candidate (spec 4.5 updated).

- Task 2, the match rule is the strict reading of spec 4.5: tokens compared exactly, given name and surname equal, a query with no middle names matches a candidate with any, a query with middle names matches only when each appears among the candidate's in the same order (an in-order subsequence), no initial expansion ("j" is not "john"). Blank names equal nothing. `personNamesEqual` takes a string or a `normalizePerson` result on either side, and `classifyRows` passes the normalized query object so nothing is re-parsed.
- Task 2, titles: honorifics (Dr, Mr, Mrs, Ms, Miss, Mx, Prof, Sir, Dame) are stripped only from the front of a name, postnominals (Esq, MD, MBBS, PhD, QC, KC) only from the back, so a surname "Dame" or a given name "Md" survives. Periods vanish ("M.D." is "md"); accents are not folded. My first read-back: every apostrophe look-alike (backtick, acute accent, prime, reversed prime, the modifier-letter apostrophes and the curly quotes, saltillo, fullwidth apostrophe) folds to `'`, and typographic dashes fold to `-`; any other punctuation between two word characters is deleted instead of becoming a space, so a stray character cannot invent a middle name ("Maria D`SOUZA" is surname "d'souza", not middle "d" plus "souza", and "D*Souza" is "dsouza"). Punctuation that really separates words stays a separator: `/ | ; : ( ) [ ] { } < > " & + =` ("Doe(MD)", "Silva/Souza"). My second read-back: a backslash in front of punctuation is a markdown escape and is dropped before folding ("Maria D\`SOUZA", "D\'SOUZA" and "D\_SOUZA" do not split the surname), and a backslash is no longer a separator (between two letters it is a stray character and is deleted).
- Task 2, a single-token input ("Wickfold") is a surname with an empty given name. `variantsFor` returns `["wickfold"]` where the registry takes a surname alone and an empty list where it does not, so the caller can say "give the full name or a number" instead of searching a form the registry cannot answer. Task 7 must handle the empty list.
- Task 2, in "SURNAME, Given" order everything before the first comma is the surname, so "VAN DER BERG, Jan" has surname "van der berg" and does not equal the natural-order "Jan van der Berg" (surname "berg"). That errs towards `ambiguous`, never towards a wrong match.
- Task 2, business names: the suffix mapping (`limited` to `ltd`, `incorporated` to `inc`, `company` to `co`, `public limited company` to `plc`, the phrase first) applies to the word wherever it stands, so both sides of a comparison are treated alike. `&` reads as `and` (Companies House treats them as the same word, and dropping `&` would make "Smith & Sons" equal "Smith Sons"). Periods and apostrophes vanish, other punctuation becomes a space ("Rolls-Royce" is "rolls royce").
- Task 2, the classifier rule (my second read-back, decided 3 Nov): zero rows is `no_match`; otherwise a row is a `match` only when its name passes `personNamesEqual` / `businessNamesEqual` against the query and exactly one row does. That includes a single returned row, whichever search variant produced it: "Christopher Wickfold" with the single row "Christine WICKFOLD" is `ambiguous` with that one candidate and `total: 1`, while a row with extra middle names, or "GREGGS P.L.C." for "Greggs PLC", is a `match`. A blank or unparseable query equals nothing, so it never matches. `classifyRows` with several rows and no row equal to the query is `ambiguous` with every row as a candidate (not `no_match`); candidates are the rows whose name equals the query's first (registry order), then the other rows (registry order), cut at `CANDIDATES_MAX`, and `total` is the full row count (my first read-back: so the cap can never drop the equal-name rows that caused the ambiguity, for example at positions 11 and 12 of a 20-row Companies House page). Each variant is explained as first name(s) then surname, or surname then a one-letter first-name initial, since `variantsFor` produces "wickfold c". A surname-only search matches no row (the match rule needs equal first names), so the goal says to open nothing. With `q.number` it searches by GMC reference number and opens the one row with exactly that number. My first read-back: the Agent decides "exactly one row matches" over every row it sees, but reports at most 10, so a register that shows 15 rows with matching rows 3 and 12 would leave one equal row among the 10 reported and the classifier would call it a match. Each now has a test that failed before the fix (two for the unbooked run, where one path was only certain from reading).
  1. **Watches asked for together passed every cap.** The slots and the visitor's count were read, then the Monitor was made (seconds), then the watch was stored, so eight requests at once all passed: one visitor got eight public watches and eight Monitors, and two visitors could put two Monitors on one record. A reservation left by a request that died stops counting after ten minutes.
  2. **The day's eight public Agent checks could be passed.** The count was read before the check was stored, so twelve checks at once were all queued. The check is now stored only while the day has room, in the same statement that counts; a visitor refused there keeps their own daily check. On the number path, a check whose page cannot be read is put in the queue and counted in one statement too. Before, it was marked for the queue first, and a run could start for it in the moment before the cap ended it, leaving that run unbooked.
  3. **One public name check could start two paid runs.** When a run found the person by name but opened nothing and the record page could not be read, the check went back for a second run by number: two runs, quoted and counted as one. A public check now ends there with that one row as its candidate, and the visitor verifies it by its number, which is a check of its own. My own checks and a Monitor's re-check still take the second run.
  4. **A run still going at 30 minutes was dropped unbooked.** The 30 minutes were counted from when the check was asked for, not from when its run started, so a check that had waited in the queue could be given up on while its run was young; and whenever a run was given up on, nothing was booked, although it was live and its callback would find the check finished. The time is now the run's own start as TinyFish reports it, and the most a run can cost ($0.208) is booked when it is given up on. The same is booked when a run's id could not be stored (`run_not_recorded`).
  5. **The shared NMC monitor would have watched November for good.** The NMC starts a new hearings page every month. The hourly job now moves the Monitor: once the month's address differs, it reads the new page once (free; the NMC may publish it late), makes the new Monitor, stores it, and only then deletes last month's. If any of that cannot be done it says so and tries again the next hour.
  6. **A Topic notice could have named the wrong result.** New results were read as places in the list counted from 0. TinyFish documents each result with its own `position`, counted from 1, and lists the new ones by that position, so the neighbouring result would have been named and the last one dropped. A new result is now found by its position. No real Topic webhook with a new result has arrived yet, so the runbook still says to check the first one.

## A running check says how long it takes, 10 November

A check that needs a real browser takes a minute or two, and its page said only "Reading the register
now". A visitor who is not told how long that takes reads a working check as a stuck one. The page now
says that a real browser takes a minute or two and how many seconds or minutes ago the check was started,
and a check waiting for the one browser says each search takes a minute or two and that the page
refreshes by itself. Live as version `967f2a6a` at 12:12 UTC.

## A waiting check shows that it is working, 10 November

A sentence was not enough. A check that reads its register inside the request gave no sign for several
seconds after the button was pressed, and a check in a real browser showed one word and a dot. The
waiting page now shows the three steps (wait for a free browser, read the register, show its answer) with
the one it is on, a bar that keeps moving, and a clock, beside the usual time. The bar has no length to
show, because a register answers when it answers, so it only says that the check is working. A page
that has stopped reloading shows no bar and no clock.

The four sites share one small script, `public/assets/wait.js`, served from the site itself and loaded
`defer`. Every page works without it. On a POST form it marks the form busy, swaps the button's words for
its `data-busy` label, shows a spinner, and refuses a second press; a page brought back by the Back button
is reset. On a waiting page it counts the clock every second between the page's own reloads. I pressed
each live button in a real browser at phone width, with the sending stopped so nothing was started: the
label changed, the form was busy, and it went once.

Live as version `8e42df78` at 12:55 UTC.

## A daily check of Standing's own readers, 14 November

A register can change its pages without notice, and a reader that no longer understands a page would
only show it when someone's lookup failed. So once a UTC day the hourly run now reads one known business
record on each register Standing reads with Fetch: GREGGS PLC (00502851) on Companies House, SANTA FE
FAMILY PHARMACY (licence 59020) on the California DCA, and PUBLIX ASSET MANAGEMENT COMPANY (P01000027088)
on Sunbiz, which is read the way a lookup reads it, through the name search and the row's own page. It
looks for the record's number, its name and a status, and writes one of three answers: understood, the
register did not answer (with Fetch's own code), or read but not understood (with what was missing). The
answer is beside each register on the Coverage page and in `reader_checks` at `/api/stats`.

The design said "The Worker has no cron that reads registries", and I changed that sentence rather than
work around it. What it protects still holds: no timer reads again a record someone looked up or watches,
and only a Monitor's report does. The check has its own table (`0002_reader_checks.sql`) and writes
nothing to checks, records, events or watches, and no evidence; a test pins that. Each run reads at most
one register, after the hourly job's own work, and a register is tried once a day whatever happens: its
row is written before the page is read, so a run that dies leaves it marked "started" and nothing tries
it again that day. A register retried every hour would be a polling loop.

The three records are businesses. GMC is left out: its pages are doctors' own records, and Standing does
not choose a person to read (spec section 7). NMC and SRA are read only by the Agent, which costs money
for each read. Each Fetch read is in the spend ledger at $0, like every other.
